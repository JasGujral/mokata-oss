// why mokata

Rules files are advice. Gates are code.

A prompt or a rules file asks the model to behave, and you find out in review whether it did. mokata moves the rules out of the prompt and into the path of the write: a hook that blocks it, an approval only a human can mint, a ledger that records it.

Prompts & rules files mokata
A test first "Please write tests first." No failing test, no implementation write — blocked by a hook.
Scope Hopes the agent stays on task. A write outside the approved spec is refused, through any tool — Write, Edit or the shell.
"Done" A claim in the chat. RED before GREEN, every criterion mapped, review recorded against the spec.
Memory Whatever got written down. No code path writes memory without your approval.
After a long session Context compacted, rules forgotten. The gate state is re-anchored after compaction — the next write is still decided by the gate.

// how it works

One run, from the idea to the merge.

Each stage has a gate. A stage you skip is a write that gets blocked, not a step that gets forgotten.

  1. 01

    Brainstorm

    Socratic questions, prior art, a pre-mortem — then you approve one approach.

    gate · approach approved
  2. 02

    Spec

    Acceptance criteria, each mapped to a test, persisted. A deferred item can't be built later without an amendment.

    gate · spec + completeness
  3. 03

    Red

    The tests fail first — proof they can catch the bug before the fix exists.

    gate · no code without a failing test
  4. 04

    Green

    Implementation inside the spec's scope only. Native edits and shell writes meet the same gates.

    gate · spec scope
  5. 05

    Review

    Checked back against the spec — by a fresh subagent when one is observed, and said plainly when it wasn't.

    gate · verdict on record
  6. 06

    Ship

    Tests green, criteria met, review passed — then you choose how it lands. mokata never merges for you.

    gate · you decide

// what you get

Four jobs, one governed engine.

enforce

The agent can't skip the process

  • Gates on native edits. Enforced by a hook on the agent's own Write, Edit and shell commands — not only on mokata's tools. A shell write meets the same verdict as a Write; a command mokata can't read is refused while a run is in progress.
  • Parallel runs, kept apart. Each Claude session is bound to its own run, so two windows working on two features never police each other.
  • Subagents under contract. A read-only explorer stays read-only, nesting is capped, and every subagent hands back a structured report.
  • Survives compaction. After /compact the gate state is re-stated from the record, so a long session can't forget it.
understand

Know what the change touches

  • A mandatory codebase graph. Blast radius answered structurally, not by grep. An embedded AST floor ships in the box; a stale graph rebuilds before it answers; a degraded answer is refused as decision input.
  • The review window. mokata ide shows what each session wrote, the diff at any point in time, branch-to-branch and PR comparisons — read-only, localhost, paired.
  • Live context. The briefing carries the repo's current state and the run's working set, inside one context budget you control.
remember

Memory you can trust

  • Can't be poisoned. Typed memory — rules, guardrails, decisions — and no code path that writes it without a human-minted approval.
  • Session notes you approve. At the end of a session mokata drafts a note from the record; it's kept only if you accept it.
  • Ages without losing anything. Bi-temporal validity: archiving closes a window instead of deleting a row.
  • Retrieval that tells the truth. Ranked in the database (FTS5 / tsvector), semantic on consent, and mokata doctor says which engine is ranking.
account

Every decision on the record

  • A typed event stream. Every gate verdict, approval and durable write — reconstruct any run: what changed, why, and who approved it.
  • Review you can measure. How many problems were caught in the loop and how many only at review, per run.
  • Waiting is legible. Every call is bounded; a gated write says AWAITING APPROVAL instead of going silent.
  • Token governance. One context budget, JIT retrieval, handback caps, output density on by default.

// questions

Before you install.

Short answers. The getting-started guide has the long ones.

Does mokata call a model or need an API key?

No. mokata never calls a model — the brain is always the agent you already run. There is no model and no API key inside mokata.

Does my code leave my machine?

No, unless you wire something that sends it. State lives under .mokata/ in your repository; team mode and sharing are opt-in, and they pass the same secret scan as every write.

What happens when a gate blocks something I want?

The block says why and what to do: approve an approach, amend the spec, add the failing test. A run-state gate can be overridden with a reason, and the override is recorded. Security blocks — a secret in the content, a write outside your workspace — cannot be overridden.

Do I have to adopt the whole pipeline?

No. mokata init --mode seatbelt gives you the gates and the graph; add memory later, or turn everything on with --mode full.

Which agents does it work with?

The full set — gates on native edits, subagent contracts, the review window per session — is Claude Code. Codex, Cursor, Copilot, Windsurf and Gemini CLI get mokata's commands, context and MCP server, and mokata says plainly what degrades.
