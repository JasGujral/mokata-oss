SI.6-DELEGATED-BLINDNESS-b — the BEHAVIOURAL harness's mutant list (0.0.17 stage 1b)
====================================================================================

Scope: the logic ADDED at stage 1b — `tests/test_si_6_behavioural_write_freedom.py`, the write-free
harness and the nine charters it binds. The static half's 26 mutants (`_writegraph_mutants.txt`) are
the parent stage's and are NOT re-run here; nothing in this stage touches that logic.

Run with `scripts/mutate.sh` and NOTHING ELSE (doc 85 §7b): only it purges the stale `.pyc`, sets
PYTHONDONTWRITEBYTECODE=1, and traps EXIT/INT/TERM so an interrupted run cannot leave the tree
mutated. Each mutant's exact invocation is written out below so the run is reproducible verbatim.

RED = the mutation was caught. GREEN = it SURVIVED. BROKEN = no verdict (never read as either).

WHY THIS LIST HAS TWO GROUPS. A behavioural pin can be weak in two independent ways, and only
mutating both finds them. Group A asks "does the pin catch a write in its subject?" Group B asks
"could the pin pass while asserting nothing?" — the failure mode the whole stage is built around,
and the one 0.0.17 has already shipped twice (WINDOW_HOLDER, doc 85 §7e; stage 16's leak test).

C is a CONTROL whose expected verdict is GREEN and is scored separately, never in the kill-rate.

  M06  `assert_write_free` stops checking the evidence   P10's (a)/(b): without it a no-op

  M07  the `MissingEvidence` refusal never fires         a binding with no "it really ran" check

  M08  the falsifiability control neuters nothing        `_noop_like` hands back the REAL

  M10  ...and the same on its STATICMETHOD branch        M08 replaces one of `_noop_like`'s two
                                                         returns, so it reaches 8 of the 9

                                                         staticmethod and stays correctly

GROUP C — control. Expected GREEN, scored separately.
------------------------------------------------------------------------------------

  M09  fts5_available leaves its probe table behind      The register entry claims the probe
       (the DROP is deleted)                             "runs against the `temp` schema … so
                                                         nothing durable is touched at all". If
                                                         that is true, dropping or not dropping
                                                         changes no durable byte and this MUST
                                                         survive. A RED here would mean the temp
                                                         schema reaches the disk and the entry is
                                                         wrong. The mutant is here to show the
                                                         pin measures DURABILITY rather than
                                                         reacting to any edit at all.
