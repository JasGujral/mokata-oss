THE TWO SURVIVORS, AND WHAT THEY WERE ACTUALLY SAYING
─────────────────────────────────────────────────────
As first written, the destination-side guard had TWO defences stopping it from treating the
public mirror's own `.git` as a foreign checkout: `find . -mindepth 2` and a `case` filter on the
resulting path. Removing either one alone changed nothing, because the other silently covered it.
Both mutants therefore came back GREEN.

That is not a gap in the tests — no single-mutant harness can kill a redundant pair, and writing a
test to chase one would have pinned an implementation detail rather than a behaviour. It is a
finding about the code: the redundancy made a load-bearing line ungradable, and `_check_internal`
ends in `rm -rf`, so the line in question is the one standing between a release run and deleting
the public checkout's git directory. "Ungradable and one edit away from catastrophic" is the worst
pair of properties a line can have.

Collapsed to a SINGLE defence — `find . -path ./.git -prune -o -name .git -print`, which neither
walks nor reports the mirror's own checkout. The prune is now the only thing doing that job, so
deleting it is immediately visible: M19 below removes it and the run goes RED with 7 failures, the
first of which is the public checkout losing its `.git`. One defence that can be graded beats two
that cannot.

The source-side scan keeps its `-mindepth 2` + `case` pair deliberately and is NOT mutated for it.
The stakes are not symmetric: a false positive there adds one redundant `--exclude` and nothing
else, while on the destination side it runs `rm -rf`. Rigor is spent where the consequence is.
